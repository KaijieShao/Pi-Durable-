# Durable Telegram replies and delivery limits

Commands and their required replies already share a SQLite FULL-synchronous transaction. Unique Telegram update IDs prevent redelivered commands from creating a second task or acknowledgement. Required replies remain in a persisted outbox until Telegram confirms delivery. Network/5xx/401 errors retry with exponential backoff (1 second to 60 seconds), without a retry-count discard. A 429 persists a bot-wide hold honoring `retry_after`, including across restarts. Progress coalescing intentionally replaces older unsent progress for a task; it never replaces a required reply. Permanent 4xx refusals remain visibly failed for owner inspection, not silently successful.

Each HTTP send now persists a metadata-only attempt **before** transmission. Success, failure kind/status, rate limits and unconfirmed outcomes are recorded in `outbox_delivery_attempts`; successful message IDs are committed atomically with the outbox and task reply mapping. INFO logs carry the outbox/attempt/message IDs and delivery latency, never text or credentials. `owner status` separately counts unconfirmed attempts. These counts are not a count of proven lost replies.

Command logs also record Telegram's original `telegram_date_s` and the exact `received_at_ms` stored with the command. Join them by update ID to the required outbox reply and its confirmed receipt. Report Telegram-timestamp-to-confirmation and server-receive-to-confirmation separately; the former has one-second input precision. Neither measures coding completion. Do not substitute server receipt time for the user's Telegram timestamp when assessing acknowledgement latency.

## Connection reuse and acknowledgement timing

The Telegram client owns a bounded HTTP/1.1 pool with four connections and a 60-second idle ceiling, respecting server keep-alive hints. Node's default fetch dispatcher can expire a connection after four idle seconds. Paced group traffic just beyond that boundary then repeatedly pays for TCP/TLS setup. A held long poll needs a separate connection from outbound replies. The pool is scoped to this client; it does not replace the relay/GitHub global dispatcher, pipeline POSTs, add hidden transport retries, or change TLS verification, request deadlines, rate-limit holds or the durable outbox rules. Shutdown stops polling and outbound work before closing its pool.

Regression tests check connection reuse after a real 4.5-second idle interval, an outbound reply while a long poll remains held, abort/close behavior and isolation from the global dispatcher. These are transport tests, not a substitute for real Telegram stress measurements. Split a live sample into Telegram timestamp → durable receipt, receipt → send attempt, and attempt → confirmed response; correlate with socket/host metrics. Preserve all failed rounds, and begin a separately reported series after any build change. A lower transport cost alone does not establish the two-second end-to-end target.

References: [Node fetch custom dispatcher](https://nodejs.org/api/globals.html#custom-dispatcher), [Undici client connection and keep-alive options](https://undici.nodejs.org/api/Client).

If Telegram confirms acceptance but SQLite temporarily cannot commit it, the live sender keeps the receipt and retries only the database transaction before any further HTTP sends. This removes duplicate sends caused by that persistence-only failure window. Injected tests verify one physical accepted message per queued reply after definite pre-accept failures, 429/503 retries and transient SQLite failures.

**Strict exactly-once delivery is not guaranteed.** Telegram Bot API `sendMessage` has no caller-provided idempotency key or history readback method. Acceptance followed by a lost HTTP response, or a crash before persisting the receipt, leaves the outcome unknowable. To avoid silently dropping a required reply, the current contract retries at least once and can duplicate it. Unsettled attempts are marked uncertain on restart. A regression deliberately demonstrates this duplicate rather than labelling the feature passed. Do not confuse one outbox row or one known message ID with proof of one physical message. A live stress run must count human-visible receipts and compare them with outbox/attempt records, separately reporting 429s, pending/failed rows, unknown outcomes, duplicates and losses.

## Schema and rollback

Schema 5 adds only the delivery-attempt table/index; migration changes no task, run, approval, branch or PR records. Before deploying, stop the single poller/watchdog, take a SQLite backup and runtime/config snapshot, then start both on the same merged source SHA. Verify task-table hashes and General `/status` before testing.

An immediate rollback to schema-4 code must stop both services first. With no active workloads, make another backup, check that the only version-5 migration was the additive delivery-attempt table, then reset **only** `meta.schema_version` to 4 (retain the new table, offset, outbox and all task records) before restoring the old code. The old code ignores the extra table; the idempotent version-5 migration permits a later roll-forward. Never replace a newer live database blindly with an old file or discard Telegram offsets/accepted commands. Restore the full old SQLite backup only if there were no post-snapshot accepted changes and that fact has been verified. Do not run Terraform for runtime rollback.
